# Decisions

| # | Date | Decision | Why |
|---|---|---|---|
| D1 | 2026-10-30 | New payroll routes **coexist** with the legacy `payroll.generation.*` / `payroll.maintenance.*` routes, using different names and URLs. Legacy files are not edited, imported or deleted. | CLAUDE.md forbids deleting functionality without instruction; the legacy code is broken but routed. |
| D2 | 2026-10-30 | No DTR engine is built. Time quantities enter payroll through a `TimeInputProvider` contract; the shipped provider reads approved `payroll_time_inputs`. | No existing code calculates late/undertime/absence/OT; building a DTR belongs to the Time module and is out of scope. A future DTR plugs in as a provider. |
| D3 | 2026-10-30 | Work country/subdivision is stored on `employment_assignments` (plus optional `location_id`) instead of adding columns to `locations`. | Avoids changing the Administration module; jurisdiction is an assignment attribute anyway. |
| D4 | 2026-10-30 | New `legal_entities` table, optionally linked to `organization_general_information`. | Multi-entity support without overloading the single existing row. |
| D5 | 2026-10-30 | Payroll run approval is permission-based with enforced separation of duties (calculator ≠ reviewer ≠ approver; calculator ≠ finalizer), not `ApprovalChainResolver`. | The resolver walks a subject employee's supervisor chain; a payroll run has no subject employee. |
| D6 | 2026-10-30 | Money: bcmath strings via `Decimal` (scale 10), `decimal(19,4)` amounts, `decimal(19,8)` rates, `decimal(12,4)` quantities; precision from `currencies.minor_units`; one rounding per line. | Skill `payroll-calculation-engine`; no new dependency needed. |
| D7 | 2026-10-30 | Non-statutory rounding mode is a pay-group setting (default `half_up`, chosen by the company). Statutory lines use the rounding declared by the rule version, falling back to the pay-group mode only if the rule declares none. | Rounding for company-paid items is company policy, statutory rounding is law. |
| D8 | 2026-10-30 | No real statutory values are seeded or hard-coded. Rules are entered through the Statutory Rules screen with source metadata and verified by a different user. Only verified versions can be used in a run that is finalized. | Skill `payroll-compliance-localization`; assignment section 6 ("do not invent"). |
| D9 | 2026-10-30 | Payroll reports reuse the Reports module (`ReportRegistry` new `payroll` category, `report.payroll`), scoped by legal entity inside each report query. | Reuses existing web/Excel/PDF/print pipeline instead of a second export stack. |
| D10 | 2026-10-30 | Fix the `success` flash gap once in `HandleInertiaRequests` + layout snackbar. | CLAUDE.md "known gap"; payroll actions need feedback; one deliberate, cross-cutting fix instead of per-page workarounds. |
| D11 | 2026-10-30 | Default role grants: `payroll` role operates payroll (prepare/calculate/review); `hr_director` approves/finalizes/verifies rules; `superadmin` all; everyone gets `payslip.view_own`. `payroll.scope.all` granted to superadmin, hr_director and payroll; others need explicit entity assignments. | Separation of duties by default; single-entity installs work without extra setup; companies can re-scope. |
| D12 | 2026-10-30 | Supported pay frequencies: weekly, biweekly, semi_monthly, monthly. Compensation bases: annual, monthly, semi_monthly, biweekly, weekly, daily, hourly. | Assignment section 5; `job_offers.salary_frequency` lacks biweekly so payroll has its own list. |
| D13 | 2026-10-30 | Daily rate for salaried bases = annualized amount ÷ pay group `annual_working_days`; hourly = daily ÷ `hours_per_day`. Both are required pay-group settings with no default. | Divisors are company/localization policy; no global 8-hour or 261/313-day assumption. |
| D14 | 2026-10-30 | Run types: `regular`, `supplemental`, `reversal`. "Adjustment" is an approved `payroll_adjustments` row applied in a regular or supplemental run. | Covers adjustments, off-cycle and reversals with one lifecycle. |
| D15 | 2026-10-30 | New model names avoid every class the legacy payroll code imports but doesn't exist (`PayrollCalendar`, `PayrollDeduction`, `PayrollAccountType`, `PayrollEmployee*`, `PayrollProjectFund`, `SalaryGrade`, `SalaryMatrix`, `SalarySchedule`, `SalaryStep`). The `payroll_calendars` table's model is `PayGroupCalendar`. | The legacy payroll routes have no `can:` middleware; creating a model they import would let any logged-in user reach the new payroll tables through them. |
| D16 | 2026-10-30 | A rule version is selected by the date its own `applies_by` names (resolver evaluates each candidate), not by a date the localization code picks. | The issuance decides whether pay date or period dates govern; this keeps it data, not code. |
| D17 | 2026-10-30 | Earnings are rounded before the localization computes statutory bases. | Bases must equal what the payslip shows. |
| D18 | 2026-10-30 | PH premium categories carry the full compounded multiplier (DOLE Handbook guide tables), with explicit night/holiday/rest-day combination categories. | The Handbook compounds factors; a single additive "night differential" on the regular rate would under-pay combined hours. |
| D19 | 2026-10-30 | PH monthly contributions in non-monthly pay groups follow a required company setting (`ph.contribution_schedule`: `last_period` or `split`). | Splitting is company policy, not law (skill `payroll-country-philippines`). |
| D10a | 2026-10-30 | D10 refined: `HandleInertiaRequests` now shares `flash.success` (additive), but it is displayed by the payroll page mixin (`resources/js/mixins/payrollPage.js`), not globally. | 87 existing pages already call `showToast()` in their own success handlers; a global flash toast would show duplicates across other modules. A global display can be switched on once those pages stop toasting themselves. |
